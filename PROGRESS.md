## Phase 3 — Workout engine (this pass)

- **Models**: `WorkoutTemplate` (user-built or generated routines — exercises with per-set targetReps/targetWeight/restSeconds/tempo, per spec §17), `WorkoutSession` (a live or completed logged workout, locked from edits once `status` becomes `completed` — "historical records should not be overwritten" per spec §20), `PersonalRecord` (append-only, one doc per new best).
- **`lib/prescription.js`** and **`lib/workout-utils.js`**: `estOneRepMax` (Epley formula), `computeVolume`, and `detectAndRecordPRs` — compares every completed weighted set in a finished session against the user's all-time best per exercise, writes a `PersonalRecord` for anything that beats it, and flags the winning set.
- **`lib/streak.js`**: daily streak calculation (consecutive-day logic), updated on `User` when a session completes.
- **Builder** (`/workouts/new`): search the real exercise catalogue, add exercises, configure sets/reps/weight/rest/tempo per set, save. Reachable directly from an exercise's detail page — "Add to Workout" is a real link now, not a disabled stub.
- **Generator** (`/workouts/generate` + `POST /api/workouts/generate`): **honest disclosure — this is a rules-based generator, not AI.** It takes time/goal/muscles/equipment, queries the real Exercise collection, round-robins across muscle groups for variety, and prescribes sets via `lib/prescription.js`. Every exercise it returns is real and already in the database (satisfies spec §18's "validate against the database" requirement) — but there's no model call here. That's still Phase 5.
- **Live session** (`/sessions/[id]`): per-set rep/weight logging, a real countdown rest timer after completing a set, skip exercise, replace exercise (inline search swap), autosaves via `PATCH` as you go, and a completion flow that calculates volume/duration/PRs/streak and shows a summary.
- **History** (`/history`): persisted, read-only list of completed sessions with date/duration/volume/PR count.
- **Mobile bottom tab bar** (`components/MobileBottomNav`): a real fixed bottom nav (Home/Explore/Workouts/Coach/Progress) on screens ≤900px, per spec §66 ("bottom navigation can be used"). The Hero's mobile quick-nav pill was retired in favor of this so there's only one bottom nav element on small screens, not two stacked on each other.

**Known simplification**: PR detection only runs at session completion (not live, set-by-set) to avoid a database write on every rep logged — so the in-session PR badge only appears after you hit "Finish Workout," not the instant you log the set. Fine for now; worth revisiting if live PR celebration matters to you.

## Phase 5 — completed (this pass)

Finished the three pieces flagged as missing last time, plus fixed two real bugs found while testing against a live database.

- **AI-assisted workout generation**: `/workouts/generate` now has a Rules-based / AI-assisted toggle. AI mode still fetches the real candidate pool from Mongo first (same filters as before), then asks Gemini to pick, order, and briefly justify a selection **from that exact list by slug only** — it's never allowed to invent an exercise. The response is validated against the real candidate slugs; anything Gemini returns that isn't a real match gets dropped. If Gemini fails, is unconfigured, or returns something unparseable, it **silently falls back to the rules-based generator** and tells you why (`aiFallbackReason` in the response) rather than erroring out the whole request. Optional free-text notes field ("sore shoulder", "prioritize legs") gets passed to the model.
- **Weekly Report + Recommendations, combined**: rather than two separate always-on AI features (which would burn through free-tier rate limits fast), one Gemini call per generation produces both a factual recap of the week (`summary`) and a specific next-step suggestion (`recommendation`). New `WeeklyReport` model caches one report per user per ISO week — viewing the Progress page doesn't cost a Gemini call, only clicking Generate/Regenerate does. Lives at the top of `/progress`. Uses only real data (this week's completed sessions, volume vs. last week, new PRs) — explicitly told not to invent numbers.
- **Diagnostic logging added to `lib/gemini.js`**: every failure mode (missing key, network failure, rate limit, blocked response, empty response) now `console.error`s server-side with real detail before returning the user-facing error. If the AI Coach acts up, check your terminal running `npm run dev` — the real reason will be there.

**Two real bugs found and fixed while chasing the "zero exercises in my database" report:**
1. The 27 hand-authored exercises (Phase 2) were missing `publicationStatus` entirely — the field the Explore page and workout generator filter on (`{ publicationStatus: 'published' }`). They'd seed into Mongo but be **invisible to every filtered query**, model default notwithstanding, because of bug #2 below. Fixed: all 27 now explicitly set `publicationStatus: 'published'` in `lib/seed-data/exercises.js`.
2. `scripts/seed-exercises.mjs` used `findOneAndUpdate(..., { upsert: true })` without `setDefaultsOnInsert: true` — so on a genuinely fresh database, any field relying on a Mongoose schema default (not explicitly present in the seed data) would silently **not** get set on newly-created documents. Fixed by adding that option, and the seed script now also prints a sanity check after running (`X of Y exercises are "published"`) so this class of problem is visible immediately instead of discovered later via an empty Explore page.

**Important**: the 870 Free Exercise DB entries always had `publicationStatus` set explicitly, so they were never affected — if your Explore page is showing genuinely zero exercises (not just missing the hand-written 27), the far more likely cause is simply that `npm run seed` hasn't been run yet against your new MongoDB connection. A fresh Atlas cluster starts empty — connecting to it doesn't populate it. Run `npm run seed` after setting `MONGODB_URI` in `.env.local` and watch for the sanity-check line it now prints.

**No new dependencies. New env requirement carried over from last pass**: `GEMINI_API_KEY` must be set for both the AI Coach and these new AI features — without it, AI-assisted generation and weekly reports return a clear "AI generation needs GEMINI_API_KEY" error/fallback rather than failing silently.

Checks the new `Food` collection for a search term first; on a miss, tries Spoonacular (nutrition + image together), and only falls back to USDA + a single shared Unsplash lookup if Spoonacular fails or returns nothing. Results are cached in Mongo tagged with the search term, so a given food is only ever fetched from an external API once, total, across all users.
- **New models**: `Food` (cached nutrition + image + source/attribution), `NutritionProfile` (dietary pattern, allergies, exclusions, goal, macro targets — one per user), `MealLog` (one doc per logged food entry, macros snapshotted at log time so later corrections to the `Food` cache don't retroactively change history), `MealPlan` (AI-generated 7-day plan + shopping list, one active plan per user).
- **`lib/nutrition-context.js`** (mirrors `lib/coach-context.js`): builds a real grounding block — dietary pattern, allergies/exclusions, targets, last 15 logged foods — fed to Gemini as a system prompt for plan generation. Model is instructed to return strict JSON and to **never** include a food conflicting with a stated allergy or dietary pattern. If the user's data suggests disordered eating patterns or the request pushes toward an extreme deficit, it's instructed to break format and return a plain-text nudge toward a doctor/dietitian instead of a plan — surfaced in the UI as an advisory message, not an error.
- **New routes**: `GET/PUT /api/nutrition/profile`, `GET /api/nutrition/foods/search?q=`, `GET/POST/DELETE /api/nutrition/log`, `GET/POST /api/nutrition/plan`.
- **New components**: `FoodCard` (search result — image, macros, servings + meal-type picker, log button, shows Unsplash attribution when applicable), `MacroSummary` (today's totals vs. targets with progress bars), `MealPlanView` (collapsible 7-day plan + shopping list).
- **`/nutrition` rebuilt** into three tabs: Today (search/log/daily totals), AI Meal Plan (generate/regenerate, view by day), Preferences (dietary pattern, goal, allergy/exclusion tags, macro targets). Added to the Sidebar nav (`Salad` icon) — it wasn't linked anywhere before.
- **Config**: `img.spoonacular.com` added to `next.config.js` image domains (`images.unsplash.com` was already there from a previous pass).

**New env vars required** (added to `.env.local.example`, nothing else in `.env.local` changes): `UNSPLASH_ACCESS_KEY`, `USDA_FDC_API_KEY`, `SPOONACULAR_API_KEY`. **No new dependencies** — all three APIs are called with plain `fetch`, same as Gemini.

**Known limitations**: Spoonacular's free tier is small (~150 req/day) — caching should keep you well under it for personal/demo use, but a genuinely public deployment would exhaust it fast without a bigger plan. Meal plans are single-active-per-user (generating a new one deactivates the old rather than keeping a history list). No food-swap or "replace this meal" endpoint yet — regenerating the whole plan is the only lever right now. No shopping-list export/checkbox state. `/diet`'s hardcoded `dietPlans` (from `lib/data.js`) were explicitly flagged in the spec as needing a real-data refactor — not touched this pass, since scope here was the new `/nutrition` surface; worth a follow-up round.

## Phase 7 — Form AI (this pass)

Scoped deliberately narrow, per the agreed plan: rule-based angle checks on 5 exercises, uploaded video only (no live camera yet), text feedback only — no video/image is ever stored.

- **New dependency**: `@mediapipe/tasks-vision` (Google's Pose Landmarker — free, keyless, runs entirely client-side via WASM/WebGL). No new env vars.
- **`lib/pose-angles.js`**: pure geometry helpers on top of MediaPipe's 33-point landmark output — joint angle calculation, picks whichever body side has better landmark visibility (camera angle usually favors one side), and a hip-width-normalized "knee past ankle" offset.
- **`lib/form-rules.js`**: rule definitions for **squat, push-up, plank, lunge, deadlift** — the 5 exercises agreed on. Each rule is threshold-based geometry (e.g. squat depth + knee valgus, push-up hip sag/pike, plank hip alignment, lunge knee-past-toes, deadlift hips-rising-before-chest). `aggregateIssues()` dedupes per-frame hits and drops anything flagged fewer than 3 times, to avoid single-frame noise being reported as a real issue.
- **`components/FormCheckUpload`**: the whole pipeline runs client-side — loads the pose model lazily, steps through the uploaded video in fixed increments (not real-time playback, faster and more consistent across browsers), draws a live skeleton overlay on a canvas (never saved), runs the rule engine per sampled frame, then aggregates.
- **`FormCheckSession` model + `/api/form-check`**: the client sends only the already-computed flagged-issues list (never the video) to the server, which asks Gemini (existing `lib/gemini.js`, same `GEMINI_API_KEY`) for a short plain-language coaching summary grounded strictly in the flagged issues — instructed not to invent anything or describe the video itself, since it never sees it. If Gemini fails, the flagged issues still save and display without a summary, same fallback pattern as the coach.
- **`/form-check` page**: exercise picker, upload, analyze, results with severity-colored issue list + AI summary, recent-checks history. Linked from the Sidebar and from a "Check my form" link on `/coach`. Not added to the mobile bottom nav — it's already at 5 items and the spec is explicit about not crowding it; Sidebar (desktop) and the Coach page link cover it for now.

**Known limitations**: thresholds are approximate, not clinically validated — this is beta-quality coaching feedback, not a certified form-checking product, and the summary explicitly avoids medical language. Single-person only (assumes one body in frame). Best results with a side-on camera angle and the full body in frame. No live real-time feedback during an active workout session yet — video review only. Coverage is intentionally limited to the 5 seed exercises; extending to more exercises means writing a new rule set per exercise, not a config change.

**No new `.env.local` values required.**
